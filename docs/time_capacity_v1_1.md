# 司序 v1.1：时间候选与容量接口

本地阶段2实现；尚未发布。此文说明现有 `/api/parse` 和 `/api/conflicts` 的增量行为，**不是** v2快照接口或完整排程器。v2结构草案仍见 `task_contract_v2.md`，本轮未修改原Dify工作流或前端。默认并仅支持校园时区 `Asia/Shanghai`；输入带UTC或其他合法偏移时，换算至该时区。

## 通知解析

`POST /api/parse` 示例：

```json
{
  "text": "明天下午3点至5点在主楼405开会。",
  "reference_date": "2026-10-24",
  "timezone": "Asia/Shanghai"
}
```

相对日期必须给出用户确认的参照日；参照日通常应是通知原语境中的日期，而不是简单取今天。缺少参照时，保留警告，不强行输出带日期的结果；支持今天、明天、后天、大后天、昨天、本周/这周/下周的具体星期和今年/明年/去年。尚不支持任意自然语言日历推理。

原有 `time_points[].value` 保留为开始值，新增 `end_value` 保存明确结束；`precision` 为 `date`、`time` 或 `datetime`，`kind` 为 `point`、`interval`、`date_range` 或 `recurring_unexpanded`。日期精度不能当作零点/23:59截止或全天固定占用；无日期的时刻也不能直接排入日历。`24:00` 在带日期时规范为次日00:00，跨午夜区间需要明确的次日或结束日期。非法日期、反向区间和存在歧义的“晚上12点”不作为有效完整时间采纳。

支持阿拉伯数字和常见中文小时、半/一刻/三刻以及上午/下午/晚上等时段；不将缺少年份隐藏起来，暂定年份会出现在警告中。规则不覆盖所有中文表达。遇到重复时间、例外工作日等表达，标为尚未展开，不能把整个日期跨度当成连续占用。

`evidence` 为原文片段，`source_start`、`source_end` 是原始字符串的Unicode码点偏移，区间为左闭右开；JavaScript如需按偏移取片段，应按码点处理，不能直接假定UTF-16索引相同。`confidence` 沿用启发式分值，未经概率校准。解析结果统一为 `parsing_status=needs_confirmation`，不等于已确认任务。

原 `location` 仅在明确提取出一个地点时有值，多地点保存在 `locations` 并提示确认对应关系，尚未完成逐事项绑定。材料支持常见否定指令过滤；条件、例外与上下文指代仍需确认。这里返回的仍是通知级聚合对象，不能直接等同于可排程的单一事项。

## 冲突与容量

`POST /api/conflicts` 示例：

```json
{
  "now": "2026-10-26T09:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "availability": [
    {"start": "2026-10-26T09:00:00+08:00", "end": "2026-10-26T12:00:00+08:00"}
  ],
  "tasks": [
    {"task_id": "R", "name": "报告", "remaining_minutes": 180, "deadline": "2026-10-26T12:00:00+08:00", "must_do": true, "priority": 90},
    {"task_id": "M", "name": "会议", "fixed_time": {"start": "2026-10-26T10:00:00+08:00", "end": "2026-10-26T11:00:00+08:00"}}
  ]
}
```

此例只剩120分钟容量，180分钟工作量会报告容量不足。算法先合并个人空闲区间，与当前时刻至每个独立截止时刻求交，再扣除固定占用并集；边界采用 `[start,end)`，相邻事项不算重叠。固定事项只计占用，准备工作须单独建任务，不能双算。

`availability` 省略表示未知，`[]` 表示明确没有空闲，显式 `null` 在HTTP接口拒绝。未知时不再擅自采用工作日4小时/周末8小时，而是仅计算扣除固定事项后的物理时间上限；该上限包括睡眠等未知占用，只有超出上限才足以报告按输入耗时存在不足，通过上限检查不能确认个人能完成。

任务 `remaining_minutes` 优先于旧 `estimated_hours`，显式 `remaining_minutes:null` 表示未知，不会回退到原总耗时，更不会当成零；仅在没有该字段时，暂用预计小时数作为全部剩余量，并明确提示。返回任务将有效剩余量规范为分钟，支持再次提交时保持工作量。`completed`、`cancelled` 不计剩余量或固定占用；标为完成却传非零剩余量会拒绝。旧接口可接受 `pending`、`draft`、`confirmed`、`scheduled`、`in_progress`、`completed`、`cancelled`，但这些字段尚未接入网页的确认操作。

每个独立截止时刻只输出一份 `capacity_checks`，包含输入工作量、未知工作量项数、可用分钟、裁剪后空档及口径；未完成的逾期事项单独报告，作为仍需处理的积压量也会进入后续截止节点的累计计算。没有截止的任务会提示补信息，不能悄悄当成没有需求。

`status` 只会是 `conflicts_detected`、`information_needed` 或 `no_conflict_detected`。单项容量检查 `necessary_bound_passed` 仅表示必要条件通过，**不代表可行安排已找到**；不可拆分时长、前置依赖、办理窗口、路程和完整排程尚未检查。全部结论以所填剩余耗时和时段为条件，输入估计错误会影响结论。

推荐只有在对应事项确实涉及已发现冲突时才建议调整或可选延期；低优先级本身不再成为劝退理由。所有必须完成的事项互相冲突时，明确要求调整约束，不能用优先级排序冒充解决。

## 校验与兼容性

HTTP请求体必须是对象；仅支持标准JSON，拒绝NaN/Infinity及损坏UTF-8；任务最多500项、空闲区间最多1000项、通知最多100000字、请求体最多1MiB。时间顺序错误、字符串布尔值、负工时、非有限工时、重复非空任务ID和没有具体时刻的deadline/now会返回400，请求体超限返回413。输入无偏移的旧格式按上海时区解释，响应参照时刻带偏移；建议新前端统一发送带偏移格式。

历史构造案例 `scenario_period.start` 只有日期，`GET /api/analyze-case` 明确按当日00:00重放并在警告中说明，不能当作真实用户时刻。原数据内的旧预期结论沿用4/8小时等假设，不作为新算法的正确性答案。接口无错误重放只证明兼容读取，不证明结论准确。

原Dify仍只调用parse，尚未接入新的真实空闲时段、剩余量和结果状态，旧页面也未展示这些新字段；本轮不发布这些代码，待确认页和工作流接好后统一验收。不要把API单测通过写成产品已完成。
